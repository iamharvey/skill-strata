# SkillStrata Bench

用 24 封客服邮件（20 封示意 + 1 个匿名真实工单的 4 轮对话），对比两种做法的效果：

- **基线**：把售后政策、订单记录、商品规格和决策词表放进一个提示，让模型一次给出决策和回复。
- **分层 Skill**：L3 只抽取事实 → L4 安全/争议守卫 → 规则代码给出唯一决策 → L2 按决策写回复。

两种模式拿到的信息完全相同，只差结构。评分全部是确定性检查（正则 + 规则），不用模型打分。

> 订单、商品、政策均为示意数据。

## 打开方式

页面使用 ES Module，需要通过 HTTP 打开（不能直接双击 `file://`）：

```bash
cd demo
python -m http.server 8090
# 浏览器打开 http://127.0.0.1:8090
```

## 接入大模型

| 方式 | 说明 |
|---|---|
| OpenAI 兼容 | 填 Base URL、API Key、模型。OpenAI、DeepSeek、通义、OpenRouter、本地 vLLM / Ollama 的 `/v1` 接口均可。需服务商允许浏览器跨域。 |
| Anthropic | 填 API Key、模型，浏览器直连。 |
| 本地 CLI | 在本机运行桥接，把任意“从标准输入读提示”的 CLI 变成接口。 |

本地 CLI 桥接：

```bash
python demo/bridge/bridge.py --cmd "claude -p"            # Claude Code
python demo/bridge/bridge.py --cmd "codex exec -"         # Codex CLI
python demo/bridge/bridge.py --cmd "ollama run qwen2.5"   # Ollama
```

页面选“本地 CLI”，地址填 `http://127.0.0.1:8787`。

密钥只保存在页面内存中，刷新即清除。

## 命令行跑分

```bash
cd demo
OPENAI_API_KEY=sk-... node tools/runner.mjs run --provider openai --model gpt-4o-mini --out runs/gpt-4o-mini.json
node tools/runner.mjs run --provider bridge --base-url http://127.0.0.1:8787 --model claude-cli --out runs/claude-cli.json
```

生成的 JSON 可以在页面上“导入结果”查看明细。

## 让 Agent 充当模型（分步模式）

适合在 Perplexity Computer 等 agent 环境中运行，不需要 API Key：

```bash
node tools/runner.mjs pending  --responses runs/agent.responses.json --out pending.json
# 让 agent 逐条作答 pending.json 中的提示，结果写回 runs/agent.responses.json（{id: 原始输出}）
# 分层 Skill 的回复步骤依赖抽取结果，所以需要再执行一次 pending → 作答
node tools/runner.mjs finalize --responses runs/agent.responses.json --label "..." --out runs/perplexity-agent.js
```

`runs/perplexity-agent.js` 会作为内置结果在页面上默认展示。

## 内置结果

### v6（2026-11-11，安全/纠纷证据校验 + 人工兜底，当前页面默认展示）

v5 中 gpt5_nano 把“笼子坏了、雪貂可能跑出来”判成人身安全（C21、C22），在 C24 里安全标记还压过了纠纷标记，导致本该静默转人工的工单发出了回复。v6 不再直接相信模型给的两个高影响布尔值：

| 环节 | 做法 |
|---|---|
| L3 抽取 | `safety_risk` / `dispute` 为 true 时，必须附上客户原话（`evidence`）；提示词写明“动物笼具损坏但无人/动物受伤 ≠ safety_risk” |
| L4 校验（确定性） | 原话必须真的出现在客户邮件或历史客户消息里，而且要命中人身风险词表（受伤、急诊、律师、媒体等）或纠纷词表（chargeback、银行、PayPal、eBay、差评等） |
| 未通过 | 不走安全/纠纷分支，按普通规则决策；回复降为草稿，标记“需人工复核后再发送”并写明原因 |
| 防漏判 | 最新邮件命中人身风险词表时，即使模型判 false 也转人工；命中纠纷词但模型未判纠纷时只要求复核，不静默转人工 |
| 抽取失败 | JSON 无法解析时整单转人工，不自动回复 |

基线回答沿用 v5（基线提示词未变），只重跑 Skill 的抽取和回复。单次运行。

| 模型 | Skill v5 | Skill v6 | 全通过 | 决策准确率 | 转人工判断 | 多轮 |
|---|---|---|---|---|---|---|
| gpt5_nano | 79.7 | **86.7** | 13 → 16 / 24 | 63% → 71% | 83% → **100%** | 57.3 → 89.7 |
| claude_haiku_5_5 | 100 | 100 | 24 / 24 | 100% | 100% | 100 |

nano 的变化：

- C21、C22：这次模型没有再标 safety_risk（提示词澄清起了作用），正确给出质量升级。
- C24：纠纷原话 “going to ebay them” 通过校验，静默转人工，不再发出回复。
- C23：模型又把“不能放心关住雪貂”标成 safety_risk，原话没有命中人身风险词表，于是降级为普通质量升级并要求人工复核（这一例仍因漏掉生锈托盘失分，与安全无关）。
- 把 v5 的 nano 抽取结果放进 v6 规则重放：C21、C22 从“安全转人工”变为质量升级 + 复核，C24 变为静默转人工，C18 的误判纠纷被降级为复核；C03、C04 不受影响。可见即使提示词没有改好，校验层本身也能拦住这类误判。

仍未解决：

- nano 的 QA 类反而变差（66 → 46）：C11–C13 这次没能把商品名对到 SKU，规则因此要求补充信息。这是抽取不稳定，与本次改动的目标无关；下一步可以在 L4 加“按商品名确定性匹配 SKU”的兜底。
- 词表是正则，覆盖英文常见表达；换语种或新说法需要补词。词表只决定“能不能走高影响分支”，没命中时的结果是人工复核，不会静默放过。
- 单次运行，样本 24 例，分差不能当作稳定结论。

### v5（2026-11-11，按业务反馈修改，小模型真实 API）

业务方对 v4 回复的两点反馈：

1. 换货选项写的是“从不同批次换货并经质检”，但我们无法保证有新批次可发，也没有质检环节；人工回复也不会向客户透露内部流程（如找开发核对产品问题）。
2. 第 4 轮（客户威胁去 eBay）不需要自动回复，本质就是转人工。

对应修改：

| 改动 | 落在哪一层 | 内容 |
|---|---|---|
| 不承诺做不到的事 | 政策 + 规则 | 换货选项改为“换货（活体笼具先发新品）/ 全额退款”，删除“不同批次、质检” |
| 不暴露内部流程 | 政策 + 回复说明 + 规则 | 新增政策 19：回复不提质量团队、缺陷登记、找产品/开发核对、批次、质检；规则里的缺陷记录改名 `internal_log`，不再传给回复层；“问题未知”的模板从“与产品团队确认”改为“核实后回复” |
| 纠纷直接转人工 | 政策 + 规则 + 流水线 | 拒付/平台纠纷/差评威胁：`HANDOFF` 且 `no_reply`，不调用回复层、不给客户自动回复；规则把客户诉求、案件事实、按政策可给的处理、安全提醒整理成交接单给人工（页面详情可见）。按这一条，C03（威胁信用卡拒付）同样改为不自动回复 |
| 评分 | 用例 | C03、C24 改为检查“没有自动回复”；所有用例新增“不暴露内部流程”检查（两种模式同样适用）；修正 C21–C23 “不得要求自行修理”把“请忽略之前让您自行修理的建议”误判为违规的问题 |

- haiku 分层 Skill 本次全部通过（C12 这次也答对了，属于单次波动，不代表已修复）。C24 交接单里“托盘生锈”只记了 1 个（客户说的是 3 个都锈），抽取仍有偏差，但不影响“直接转人工”。

### 小模型真实 API（2026-11-11，24 例，v4 Skill）

用 Perplexity 模型接口直连两个小模型，提示、政策、规则、评分与 v4 完全相同，单次运行、默认采样参数（max_tokens 8000）。这是本仓库第一次用真实 API 跑分（之前都是子 agent 充当模型）。原始输出在 `runs/gpt5_nano.v4.responses.json`、`runs/claude_haiku_5_5.v4.responses.json`（v5 的原始输出为不带 v4 后缀的同名文件）。

| 模型 · 模式 | 综合得分 | 全部通过 | 违规 | 决策正确率 | 关键事实 | 多轮（C22–C24） |
|---|---|---|---|---|---|---|
| claude_haiku_5_5 · 基线 | 92.0 | 20/24 | 0 | 83% | 93% | 42.9 |
| claude_haiku_5_5 · 分层 Skill | 98.3 | 23/24 | 0 | 96% | 100% | 100 |
| gpt5_nano · 基线 | 89.5 | 14/24 | 6 | 83% | 84% | 65.5 |
| gpt5_nano · 分层 Skill | 83.9 | 14/24 | 3 | 71% | 56% | 61.5 |
| （对照）Perplexity Agent v4 · 基线 / Skill | 98.9 / 98.3 | 22 / 23 | 0 / 0 | 96% / 96% | 97% / 100% | 91.3 / 100 |

看到的现象：

1. **haiku：分层 Skill 明显更稳**。基线在多轮里出错：C22 输出的 JSON 无法解析（按 0 分计），C23 把托盘问题转了人工且没提“先发新品”，C24 转人工同时又自行给方案。分层 Skill 只错 C12（与之前一致）。
2. **nano：分层 Skill 反而更差，但违规更少**。基线的 6 处违规都是越权（擅自答应比例、在安全场景谈赔偿等），分层 Skill 把违规压到 3 处；但抽取环节的错误被确定性规则放大：
   - 把“笼子坏了、动物可能跑出”判成 `safety_risk`（应为 `animal_safety`），规则直接走“安全事件只转人工”，C21/C22 丢掉了换货/退款选项；
   - 把 C02 的“否则就退货”误判为纠纷，转了人工；
   - 订单号只写在另一个意图里时没有带过来（C19、C20），规则只能去问订单号；
   - C23 按“笼子”而不是按“问题”拆分，托盘生锈被漏掉。
3. 结论：分层的收益依赖抽取质量。抽取模型太弱时，一个布尔字段判错会让规则走进错误分支，比单提示模式错得更彻底；但“不越权承诺”这一点仍然更可靠。

评分修正：此前输出无法解析的用例会被排除出汇总（分母变小、分数虚高）；现改为按 0 分计。之前各次 agent 运行没有解析失败，结果不变。

可以做的加固（尚未实施）：对高影响字段（`safety_risk`、`dispute`）做二次确认或要求给出原文依据；同一封邮件只有一个订单号时由规则补全；抽取失败或字段冲突时降级为人工复核，而不是直接走硬分支。

### v4（2026-11-11，24 例，多轮改进）

按 v3 暴露的 4 个问题修改 Skill，并完整重跑 24 例（政策、抽取结构、回复说明都变了，72 条提示全部重新作答）。

| 改动 | 落在哪一层 | 内容 |
|---|---|---|
| 对话状态 | 抽取 + 规则 | 抽取 `previous_offers`（类型、比例、件数、是否被拒、拒绝原因）、`customer_choice`、`info_already_given`；规则据此生成 `do_not_offer`（不再提已拒方案）、`confirmed`（客户已选就直接确认）、`corrections`（收回“请自行修理”）；客户第 3 次来信起标记 `priority`。“是否曾要求自行修理”同时对我方历史回复做确定性匹配，因为模型会把它并进“部分退款” |
| 按问题拆分 | 抽取 + 规则 | 每个独立问题/部件单独一条意图（`component`），各自记录件数和是否有照片：网片损坏 2 个走质量升级，托盘生锈 3 个缺照片就单独补问 |
| 纠纷转人工 | 规则 + 回复 | 纠纷不再提前返回：保留客户的具体诉求、案件事实、按政策应得的处理（`for_specialist`，给专员看）和动物安全提醒；回复要逐条确认诉求，但不承诺结果、补偿或时限 |
| 政策 | 政策 | 活体动物笼具换货“先发新品，不需要先拆、先退或等取件”（规则 17）；新增多轮规则 18 |

| 模式 | 综合得分 | 全部通过 | 违规 | 多轮（C22–C24） |
|---|---|---|---|---|
| 基线 | 98.9 | 22/24 | 0 | 91.3 |
| 分层 Skill | 98.3 | 23/24 | 0 | 100 |
| 人工实际回复 | — | — | — | 30 / 30 / 30（按 v4 检查项；按 v3 检查项为 33 / 38 / 43）|

- 分层 Skill 的 C22–C24 全部通过；唯一失败仍是 C12（过度抽取载重问题，有意保留未修）。
- 基线失败 2 例：C22 没有收回“请自行修理”（但给了换货/全额退款且先发货）；C24 在转人工的同时又自行给出质量升级处理（违反“纠纷只转人工”）。
- 按预先写定的评审表人工复核：C22 两种做法都是 5/5；C23 基线 5/5，分层 Skill 约 4.5/5（给了“先发新品”，但没有明确回应“雪貂没地方住”，语气偏模板）；C24 两者回复内容都达标。

需要说明的局限：

1. **C22–C24 不再是独立证据**。新增的检查项（收回自行修理、先发新品、覆盖 2 个笼子、转人工保留安全提醒且不承诺方案）和 Skill 的修改都是看到 v3 结果之后做的；检查项都来自预先写定的评审表，两种模式同样适用，但仍属于“在测试集上调优”。要证明多轮能力，需要另外留出没看过的真实多轮工单。
2. **政策改动两边都受益**。基线提示里同样包含新政策，所以基线也学会了“先发新品”；基线在多轮上的下降主要来自新增的检查项，而不是能力变差。
3. **评分器修正**：C03 的“不得承诺退款”规则把“已记录您的全额退款请求”误判为承诺，两种模式同时中招；已加入例外并重新评分。这也是看到结果后的修改。
4. 单次运行，由 Perplexity Computer 子 agent 充当模型，没有测真实 API 的稳定性与成本；换小模型时差距可能不同。

v3 的原始输出保存在 `runs/agent.v3.responses.json`（提示已变，不能用当前代码回放）。

### v3（2026-11-11，24 例，含多轮）

C22–C24 是 C21 同一工单的第 2–4 轮。每轮给模型“到上一轮为止的真实对话”（含人工客服当时实际发出的回复），让它写本轮回复，再与人工实际回复对照。被测的是 v2 版 Skill，没有针对多轮做任何改动；只补了对话历史的呈现方式，并把订单数据更正为“一单 3 个笼子”。评审标准在看到输出前写定，见 [docs/c21-thread-rubric.md](../docs/c21-thread-rubric.md)。

| 模式 | 综合得分 | 全部通过 | 违规 | 多轮（C22–C24） |
|---|---|---|---|---|
| 基线 | 100.0 | 24/24 | 0 | 100 |

分层 Skill 在多轮里暴露的问题（均为设计缺口，不是模型失误）：

1. **没有对话状态**：规则不知道之前给过什么方案、客户拒绝了什么（如“取件期间雪貂没地方住”），第 3 轮又原样列出两个选项。
2. **一类问题只能抽成一条**：第 3 轮新出现的“托盘生锈”被并进了客户诉求字段，规则没有为它补要照片；`units_affected` 把网片损坏（2 个）和生锈（3 个）混成了 3 个。
3. **纠纷转人工的模板太单薄**：第 4 轮按“拒付/纠纷”规则转人工，回复只剩两句；而且纠纷分支提前返回，连动物安全提醒也丢了。
4. **政策缺口**：活体动物笼具的换货应“先发新品、不要求先退回”，政策里没有，两种做法都只能回避。

### C21：真实工单带来的改动

C21 来自一封真实 eBay 工单：客户的第 2 个兔笼前门网片焊点断裂，笼里是雪貂。v1 版 Skill 在这封邮件上的表现不如基线：两者都去索要订单号，Skill 的回复只剩一句话，既没提重复问题也没提动物安全。人工原回复给了 15% 折扣并让客户自行修理，按本仓库标准得 20 分、2 项违规。

据此做了四处改动，两种模式共享同一份政策与数据：

1. **抽取字段**：新增 `animal_safety`（围栏损坏、动物可能逃逸或受伤）、`repeat_issue` / `units_affected`（第 2 件起同样问题）；`severity` 扩展到质量缺陷；邮件新增渠道信息，平台订单由系统按 平台 + 买家 + 商品号 关联（`lookupChannelOrders`），不再向客户索要。
2. **规则**：同一产品的结构性缺陷再次出现（客户说明，或系统记录中有同类工单）→ `QUALITY_ESCALATION`：上报质量团队并按 SKU 记录，客户可选“换另一批次并质检后的新品”或“全额退款”；订单 > 300 USD 改为转人工审批；不得让客户自行修理。客户没提“第 2 个”时，规则也会凭订单记录识别重复（见 `tools/selftest.mjs`）。
3. **回复**：决策中带 `safety_notice` 时，L2 必须原样写入固定的安全提醒。
4. **用例**：C21 加入用例集。客户名、商品号已替换；原图不公开，改为图片识别步骤生成的文字描述，两种模式看到的内容相同。

怎么读：

- **C21 通过不是独立证据**：这一轮的改动正是由它引出的。更有意义的是其余 20 例没有退步。
- 真正起作用的主要是“数据和政策补齐”（渠道订单关联、商品目录、重复缺陷规则），这些同样写进了基线的提示里，所以基线也通过了。分层 Skill 的不同在于：结论由代码给出，可以单测、可以审计；15% 折扣在结构性缺陷下根本不会出现，而基线是靠模型每次都“遵守”。
- 单次运行、n=21、由 agent 充当模型。
